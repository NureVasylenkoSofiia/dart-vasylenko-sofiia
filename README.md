# Розклад занять групи

Консольний проєкт мовою Dart для роботи з розкладом занять університетської групи. Розробляється в межах лабораторних робіт із дисципліни «Програмування мовою Dart».

Василенко Софія Олександрівна, ПЗПІ-23-3.

### Про програму

Програма працює з розкладом занять, який містить назву дисципліни, викладача, тип заняття, день тижня, час початку, аудиторію та дату. Початкові дані складаються з 15 текстових записів, три з яких навмисно містять помилки для перевірки їх обробки.

У першій лабораторній роботі обробку даних реалізовано за допомогою функцій, колекцій та Dart Records без власних класів. У другій лабораторній ту саму програму перероблено на об'єктно-орієнтовану модель. Основна функціональність збереглася: розбір і перевірка даних, фільтрація, групування, сортування, підрахунок статистики та формування текстового звіту. У третій лабораторній роботі об'єктну модель доповнено асинхронним шаром доступу до даних, потоковою обробкою подій розкладу та паралельним виконанням важких обчислень за допомогою ізолятів. Для перевірки асинхронних операцій і потоків реалізовано модульні тести.

### Лабораторна робота №1. Функції та обробка колекцій

Точка входу знаходиться у `bin/group_schedule.dart`, а логіку обробки винесено до `lib/`. Початкові записи зберігаються у `schedule_data.dart`, розбір виконується у `schedule_parser.dart`, перевірка — у `schedule_validator.dart`. Для статистики та сортування використовується `schedule_statistics.dart`, для формування звіту — `schedule_report.dart`, а допоміжні функції знаходяться у `schedule_utils.dart`. Такий поділ дозволяє не розміщувати всю логіку в одному файлі та повторно використовувати окремі функції.

Вхідні дані представлені як `const List<String>`, оскільки за умовою вони мають бути текстовими рядками з роздільником. Після розбору використовується типізований Record `ScheduleEntry`. Він дозволяє звертатися до полів за назвами без оголошення власного класу. Альтернативою було використання класу-сутності, але для ЛР1 це не відповідало обмеженню завдання.

Час початку зберігається як `int` — кількість хвилин від початку доби, що спрощує порівняння та сортування. Для дат використовується `DateTime`, для групування — `Map<String, List<ScheduleEntry>>`, а для отримання унікальних назв дисциплін — `Set<String>`. Останній варіант зручніший за ручний пошук повторень.

Розбір реалізовано через `split()` і `tryParse()`, щоб некоректні записи не спричиняли аварійного завершення програми. Для обробки колекцій використовуються `where()`, `map()` і `fold()`. Сортування виконується над копією списку, для формування тексту застосовано `StringBuffer`, а для нумерації записів — замикання, яке зберігає значення лічильника між викликами. Перевірка аудиторій використовує `RegExp` з іменованими групами та `replaceAllMapped()`, а обчислення різниці між датами — `DateTime.difference()` і `Duration`.

### Лабораторна робота №2. Об'єктно-орієнтована модель

У другій лабораторній роботі представлення занять змінено з Record на незмінний клас `Lesson`, оголошений у `lesson.dart`. Його поля мають модифікатор `final`, а для створення об'єктів передбачено генеративний конструктор, іменований `fromCsv` та фабричний конструктор, який повертає стандартне заняття.

Окремо створено `LessonPrimary` з первинним конструктором Dart 3.13. Порівняння двох варіантів показало, що первинний конструктор скорочує повторення полів і параметрів, але за однакових вхідних даних поведінка об'єкта залишається такою самою.

Для порівняння занять за значеннями полів перевизначено `==` і `hashCode`. Під час перевірки два однакові об'єкти утворювали один елемент у `Set`. Після тимчасового вилучення `hashCode` множина містила два елементи, а аналізатор повідомляв про відсутність відповідного перевизначення. Після експерименту правильну реалізацію було відновлено.

Ієрархію типів занять побудовано на основі `sealed class LessonKind` із підтипами для лекції, практики, лабораторної роботи та семінару. Кожен підтип має власні характеристики, а спільний метод `describe()` демонструє поліморфізм. Рекомендації для занять визначаються через `switch` без `default`. Під час додавання четвертого підтипу аналізатор виявив помилку `non_exhaustive_switch_expression`, яка зникла після доповнення `switch`.

Для лекцій і семінарів використано домішку `PreparationMaterials on LessonKind`. Вона додає спільний метод підготовки матеріалів без створення додаткового рівня успадкування. Обмеження `on` дозволяє застосовувати домішку до відповідних підкласів і звертатися до властивостей базового типу.

У `repository.dart` реалізовано узагальнене сховище `Repository<T extends Identifiable>`. Обмеження типу гарантує наявність властивості `id`, необхідної для зберігання та пошуку об'єктів у `Map<String, T>`. Ідентифікатор заняття обчислюється з його характеристик. Для навчального набору цього достатньо, хоча в реальній системі доцільніше було б використовувати окремий стабільний ідентифікатор.

Категорії занять також представлені розширеним переліченням `LessonType` з полями, конструктором і методами. Для форматування дат реалізовано `ScheduleDateExtension` на типі `DateTime`. Результат розбору рядка повертається через Record з полями `lesson` та `error`, а деструктуризація дозволяє отримувати обидва значення. У `lesson_patterns.dart` використано зіставлення зі зразком з охоронцем `when` для визначення рекомендацій за характеристиками заняття.

Розбір, валідацію та агрегацію з ЛР1 перенесено на об'єкти `Lesson`. Для цього використовуються `lesson_parsing.dart`, `lesson_validator.dart`, `lesson_schedule_service.dart`, `lesson_statistics.dart` і `lesson_report.dart`. Основна демонстрація знаходиться у `bin/lab2_demo.dart`. Результати залишилися такими самими: із 15 записів 12 проходять перевірку, визначено чотири лабораторні заняття та шість унікальних дисциплін.

### Лабораторна робота №3. Асинхронна та паралельна обробка даних

На основі моделі ЛР2 створено асинхронне сховище `AsyncRepository<T extends Identifiable>`, яке підтримує завантаження, збереження та видалення об'єктів через `Future`. Для імітації звернення до зовнішнього джерела даних використано `Future.delayed()`. Тривалість затримки задається через конструктор, що дозволяє скоротити час виконання модульних тестів.

У файлі `analysis_options.yaml` увімкнено правила `unawaited_futures` і `discarded_futures`. Експерименти із забутим `await` показали, що програма може продовжити виконання до завершення асинхронної операції, а звичайний `try/catch` без очікування не перехоплює помилку, яка виникає пізніше.

За допомогою `Stopwatch` порівняно послідовне та одночасне очікування трьох операцій із затримкою 500 мс. Послідовне виконання зайняло 1530 мс, а використання `Future.wait` — 513 мс. Для обробки помилок групи операцій також використано `.wait` і `ParallelWaitError`, що дозволяє отримати інформацію як про невдалі операції, так і про успішні результати.

Метод `watchAll()` реалізовано як генератор `async*`, який поступово видає збережені заняття. Під час перевірки підтверджено, що тіло генератора починає виконуватися лише після підписки на потік.

Для подій додавання, зміни та видалення занять створено класи `LessonEvent` і `LessonEventService`. Джерелом подій є `StreamController<LessonEvent>`. Продемонстровано буферизацію подій до підписки, обробку помилок через `await for` і `listen()`, різницю між одноразовими та широкомовними потоками. Для явних підписок використовується `StreamSubscription` із подальшим скасуванням через `cancel()`. Трансформацію потоку реалізовано через `where()`, `map()` і `take()`.

Для демонстрації паралельних обчислень створено функцію `calculateHeavyStatistics()`, яка підраховує навчальне навантаження за днями тижня на основі 20 мільйонів згенерованих записів. Порівняно виконання в основному ізоляті та через `Isolate.run`. Результати обчислень збігаються. Окремий експеримент підтвердив, що зміна глобальної змінної в іншому ізоляті не впливає на її значення в основному.

Для перевірки реалізації написано вісім нових модульних тестів у файлах `async_repository_test.dart` та `lesson_event_service_test.dart`. Використано `group`, `setUp`, `expectLater`, `emitsInOrder` і `emitsError`. Перевірено операції сховища, порядок надходження занять, буферизацію подій та обробку помилок у потоці. Разом із попереднім тестом проєкту успішно пройдено дев'ять тестів.

### Залежності та прийняті рішення

Для основної логіки програми сторонні пакети не потрібні. У `pubspec.yaml` використано залежності для розробки: `lints` для правил статичного аналізу та `test` для автоматизованого тестування в наступних лабораторних роботах. Замість `lints` можна було налаштувати власний набір правил, а для простих перевірок використовувати `assert` замість `test`. Стандартні пакети залишено для подальшого розвитку проєкту.

Пакет `path`, який був доданий початковим шаблоном Dart, прибрано з прямих залежностей, оскільки програма його не використовує. Для розбору текстових записів також не додавався окремий CSV-парсер: для фіксованого формату із сімома полями достатньо `split()`.

Під час розробки ЛР2 розглядалися й інші варіанти реалізації. Замість узагальненого `Repository` можна було створити окреме сховище лише для занять, замість `sealed`-ієрархії — використовувати звичайні рядкові категорії, а спільну поведінку лекцій і семінарів дублювати в кожному класі. Обраний підхід дозволяє краще розділити відповідальність між компонентами та повторно використовувати їх.

У ЛР3 модифікатор `late` використовується в модульних тестах для змінних, які ініціалізуються у `setUp()` перед кожним тестом. Тип `dynamic` явно не використовується. Оператор `!` застосовується для логічного заперечення, а для роботи з nullable-значеннями використовуються перевірки на `null`, оператори `??` та `?.`. У функції маскування з ЛР1 застосовано `as RegExpMatch` для доступу до іменованих груп регулярного виразу.

Для ЛР3 нових сторонніх залежностей не додавалося. Асинхронність, потоки та ізоляти реалізовано стандартними засобами `dart:async` і `dart:isolate`. Замість справжнього доступу до файлів або мережі використано імітацію затримок, як передбачено завданням. Для потокової обробки обрано `StreamController`, оскільки він дозволяє явно керувати подіями та помилками. Пакет `test` використовується для автоматизованої перевірки асинхронних операцій замість ручних перевірок через `print()` або `assert`.

### Організація Git

Лабораторні роботи виконуються в одному репозиторії з використанням окремих гілок для збереження історії розробки:

## Лабораторна робота №4. Модульний застосунок

У лабораторній роботі №4 проєкт розкладу занять було доповнено роботою з файловою системою, JSON, HTTP-запитами та власним HTTP-сервісом.

Основну логіку розміщено в каталозі `lib/`, а внутрішню реалізацію — в `lib/src/`. У каталозі `bin/` знаходяться точки входу консольного застосунку, HTTP-сервера та демонстраційні програми. Для доступу до основних можливостей пакета використовується `lib/group_schedule.dart`.

### Основні можливості

- Перегляд занять із JSON-файлу та фільтрація за дисципліною.
- Додавання занять через командний рядок.
- Збереження та завантаження розкладу у форматі JSON.
- Потокове читання великих текстових файлів через `openRead()`.
- Отримання державних свят із зовнішнього REST API.
- HTTP-сервіс на базі `shelf` з маршрутами GET і POST.
- Автоматизоване тестування роботи застосунку.

### Запуск консольного застосунку

Перегляд довідки:

```powershell
dart run bin/schedule_cli.dart --help
```

Перегляд усіх занять:

```powershell
dart run bin/schedule_cli.dart list
```

Фільтрація за дисципліною:

```powershell
dart run bin/schedule_cli.dart --subject "Математика" list
```

Отримання державних свят:

```powershell
dart run bin/schedule_cli.dart --year 2026 --country UA holidays
```

Для додавання заняття використовується команда `add` з опцією `--csv`. Дані записуються у JSON-файл у каталозі `data/`.

### Запуск HTTP-сервера

```powershell
dart run bin/schedule_server.dart
```

Сервер запускається локально за адресою `http://127.0.0.1:8080`.

Реалізовані маршрути:

- `GET /items` — отримання всіх занять із можливістю фільтрації через параметр `subject`.
- `GET /items/<id>` — отримання заняття за URL-безпечним ідентифікатором.
- `POST /items` — додавання нового заняття з JSON-тіла запиту.

Для неправильних запитів передбачено HTTP-статуси 400, 404 та 409. Журналювання HTTP-запитів реалізовано через middleware `logRequests()`.

### Залежності

Для реалізації роботи використано такі пакети:

- `path` — формування шляхів до файлів незалежно від операційної системи. Альтернатива — ручне складання шляхів, але воно менш надійне.
- `args` — розбір команд та опцій командного рядка. Альтернатива — самостійний розбір списку аргументів.
- `http` — HTTP-запити до зовнішнього REST API. Альтернатива — `dart:io` та `HttpClient`, які потребують більше низькорівневого коду.
- `shelf` — обробка HTTP-запитів і middleware. Альтернатива — власний сервер через `HttpServer`.
- `shelf_router` — маршрутизація HTTP-запитів. Альтернатива — ручна перевірка шляху та методу запиту.

Для розробки використовуються:

- `test` — модульне тестування. Розміщено в `dev_dependencies`, оскільки пакет потрібен під час перевірки коду, але не для звичайного запуску застосунку.
- `lints` — правила статичного аналізу Dart. Альтернатива — власний набір правил аналізатора.

JSON-серіалізація реалізована вручну через `toJson()` і `fromJson()`, без кодогенерації, відповідно до вимог лабораторної роботи.

### Перевірка проєкту

Форматування коду:

```powershell
dart format .
```

Статичний аналіз:

```powershell
dart analyze
```

Запуск модульних тестів:

```powershell
dart test
```

Під час останньої перевірки успішно пройдено 36 тестів, а `dart analyze` не виявив зауважень.

Для генерації документації публічного API використовується команда:

```powershell
dart doc
```

Згенеровані файли розміщуються в `doc/api/` і не додаються до репозиторію.

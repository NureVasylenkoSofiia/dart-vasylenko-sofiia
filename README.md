# Розклад занять групи

Консольний проєкт мовою Dart для роботи з розкладом занять університетської групи. Розробляється в межах лабораторних робіт із дисципліни «Програмування мовою Dart».

Василенко Софія Олександрівна, ПЗПІ-23-3.

### Про програму

Програма працює з розкладом занять, який містить назву дисципліни, викладача, тип заняття, день тижня, час початку, аудиторію та дату. Початкові дані складаються з 15 текстових записів, три з яких навмисно містять помилки для перевірки їх обробки.

У першій лабораторній роботі обробку даних реалізовано за допомогою функцій, колекцій та Dart Records без власних класів. У другій лабораторній ту саму програму перероблено на об'єктно-орієнтовану модель. Основна функціональність збереглася: розбір і перевірка даних, фільтрація, групування, сортування, підрахунок статистики та формування текстового звіту.

### Лабораторна робота №1. Функції та обробка колекцій

Точка входу знаходиться у `bin/group_schedule.dart`, а логіку обробки винесено до `lib/`. Початкові записи зберігаються у `schedule_data.dart`, розбір виконується у `schedule_parser.dart`, перевірка — у `schedule_validator.dart`. Для статистики та сортування використовується `schedule_statistics.dart`, для формування звіту — `schedule_report.dart`, а допоміжні функції знаходяться у `schedule_utils.dart`. Такий поділ дозволяє не розміщувати всю логіку в одному файлі та повторно використовувати окремі функції.

Вхідні дані представлені як `const List<String>`, оскільки за умовою вони мають бути текстовими рядками з роздільником. Після розбору використовується типізований Record `ScheduleEntry`. Він дозволяє звертатися до полів за назвами без оголошення власного класу. Альтернативою було використання класу-сутності, але для ЛР1 це не відповідало обмеженню завдання.

Час початку зберігається як `int` — кількість хвилин від початку доби, що спрощує порівняння та сортування. Для дат використовується `DateTime`, для групування — `Map<String, List<ScheduleEntry>>`, а для отримання унікальних назв дисциплін — `Set<String>`. Останній варіант зручніший за ручний пошук повторень.

Розбір реалізовано через `split()` і `tryParse()`, щоб некоректні записи не спричиняли аварійного завершення програми. Для обробки колекцій використовуються `where()`, `map()` і `fold()`. Сортування виконується над копією списку, для формування тексту застосовано `StringBuffer`, а для нумерації записів — замикання, яке зберігає значення лічильника між викликами. Перевірка аудиторій використовує `RegExp` з іменованими групами та `replaceAllMapped()`, а обчислення різниці між датами — `DateTime.difference()` і `Duration`.

### Лабораторна робота №2. Об'єктно-орієнтована модель

У другій лабораторній роботі представлення занять змінено з Record на незмінний клас `Lesson`, оголошений у `lesson.dart`. Його поля мають модифікатор `final`, а для створення об'єктів передбачено генеративний конструктор, іменований `fromCsv` та фабричний конструктор, який повертає стандартне заняття.

Окремо створено `LessonPrimary` з первинним конструктором Dart 3.13. Порівняння двох варіантів показало, що первинний конструктор скорочує повторення полів і параметрів, але за однакових вхідних даних поведінка об'єкта залишається такою самою.

Для порівняння занять за значеннями полів перевизначено `==` і `hashCode`. Під час перевірки два однакові об'єкти утворювали один елемент у `Set`. Після тимчасового вилучення `hashCode` множина містила два елементи, а аналізатор повідомляв про відсутність відповідного перевизначення. Після експерименту правильну реалізацію було відновлено.

Ієрархію типів занять побудовано на основі `sealed class LessonKind` із підтипами для лекції, практики, лабораторної роботи та семінару. Кожен підтип має власні характеристики, а спільний метод `describe()` демонструє поліморфізм. Рекомендації для занять визначаються через `switch` без `default`. Під час додавання четвертого підтипу аналізатор виявив помилку `non_exhaustive_switch_expression`, яка зникла після доповнення `switch`.

Для лекцій і семінарів використано домішку `PreparationMaterials on LessonKind`. Вона додає спільний метод підготовки матеріалів без створення додаткового рівня успадкування. Обмеження `on` дозволяє застосовувати домішку до відповідних підкласів і звертатися до властивостей базового типу.

У `repository.dart` реалізовано узагальнене сховище `Repository<T extends Identifiable>`. Обмеження типу гарантує наявність властивості `id`, необхідної для зберігання та пошуку об'єктів у `Map<String, T>`. Ідентифікатор заняття обчислюється з його характеристик. Для навчального набору цього достатньо, хоча в реальній системі доцільніше було б використовувати окремий стабільний ідентифікатор.

Категорії занять також представлені розширеним переліченням `LessonType` з полями, конструктором і методами. Для форматування дат реалізовано `ScheduleDateExtension` на типі `DateTime`. Результат розбору рядка повертається через Record з полями `lesson` та `error`, а деструктуризація дозволяє отримувати обидва значення. У `lesson_patterns.dart` використано зіставлення зі зразком з охоронцем `when` для визначення рекомендацій за характеристиками заняття.

Розбір, валідацію та агрегацію з ЛР1 перенесено на об'єкти `Lesson`. Для цього використовуються `lesson_parsing.dart`, `lesson_validator.dart`, `lesson_schedule_service.dart`, `lesson_statistics.dart` і `lesson_report.dart`. Основна демонстрація знаходиться у `bin/lab2_demo.dart`. Результати залишилися такими самими: із 15 записів 12 проходять перевірку, визначено чотири лабораторні заняття та шість унікальних дисциплін.

### Залежності та прийняті рішення

Для основної логіки програми сторонні пакети не потрібні. У `pubspec.yaml` використано залежності для розробки: `lints` для правил статичного аналізу та `test` для автоматизованого тестування в наступних лабораторних роботах. Замість `lints` можна було налаштувати власний набір правил, а для простих перевірок використовувати `assert` замість `test`. Стандартні пакети залишено для подальшого розвитку проєкту.

Пакет `path`, який був доданий початковим шаблоном Dart, прибрано з прямих залежностей, оскільки програма його не використовує. Для розбору текстових записів також не додавався окремий CSV-парсер: для фіксованого формату із сімома полями достатньо `split()`.

Під час розробки ЛР2 розглядалися й інші варіанти реалізації. Замість узагальненого `Repository` можна було створити окреме сховище лише для занять, замість `sealed`-ієрархії — використовувати звичайні рядкові категорії, а спільну поведінку лекцій і семінарів дублювати в кожному класі. Обраний підхід дозволяє краще розділити відповідальність між компонентами та повторно використовувати їх.

`late` і `dynamic` у реалізації лабораторних робіт не використовуються. Оператор `!` застосовується для логічного заперечення, зокрема у перевірках коректності аудиторії, а не для примусового розпакування nullable-значень. Для роботи з відсутніми значеннями використовуються перевірки на `null`, `??` і `?.`. У функції маскування з ЛР1 застосовано `as RegExpMatch` для доступу до іменованих груп регулярного виразу.

### Організація Git

Лабораторні роботи виконуються в одному репозиторії з окремими гілками для збереження історії розробки.

- `main` — завершена реалізація лабораторної роботи №1.
- `lab2` — об'єктно-орієнтована реалізація лабораторної роботи №2.

Гілка `lab2` створена на основі `main`, тому містить попередню версію програми та всі зміни другої лабораторної. Роботу над ЛР2 розподілено на окремі етапи з комітами в різні дні. Після завершення перевірок зміни планується об'єднати з `main`, зберігши гілку `lab2` для перегляду її історії.

Посилання на гілки:

- [ЛР2 — lab2](https://github.com/NureVasylenkoSofiia/dart-vasylenko-sofiia/tree/lab2)

### Запуск і перевірка

Для роботи потрібен Dart SDK версії 3.13 або новішої. Команди виконуються з кореневої папки проєкту.

Завантаження залежностей:

```powershell
dart pub get
```

Запуск першої лабораторної:

```powershell
dart run bin/group_schedule.dart
```

Запуск другої лабораторної:

```powershell
dart run bin/lab2_demo.dart
```

Перевірка форматування та аналіз коду:

```powershell
dart format .
dart analyze
dart fix --dry-run
```

Після завершення ЛР2 статичний аналіз не виявив зауважень (`No issues found!`), а команда `dart fix --dry-run` не запропонувала автоматичних виправлень (`Nothing to fix!`).
